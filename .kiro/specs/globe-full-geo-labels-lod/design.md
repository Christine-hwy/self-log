# Design Document: globe-full-geo-labels-lod

## Overview

This feature replaces the hand-picked `worldLocations.ts` dataset with a generated, comprehensive dataset covering all sovereign countries (from `world-countries`) and a population-tiered set of cities (from `all-the-cities`), and reworks `GlobeView.tsx`'s label rendering to filter which labels are passed into `htmlElementsData` based on the current camera altitude, instead of rendering every label as an always-present DOM node whose opacity is toggled by CSS.

**Key architectural decision — generate, don't ship raw datasets to the browser:** `all-the-cities` ships ~138,398 city records (~6.4MB unpacked) intended for Node/MongoDB use, and `world-countries` ships rich metadata (translations, flags, borders, etc.) far beyond what's needed here. Importing either package directly into the Vite/browser bundle would bloat bundle size dramatically and includes fields irrelevant to this feature. Instead:

- `world-countries` and `all-the-cities` are added as **devDependencies** (build-time only, never shipped to the browser).
- A one-time Node generation script (`scripts/generate-geo-labels.mjs`) reads both packages, filters/maps them into the minimal shape needed, and writes a small static TypeScript data file `src/data/geoLabels.ts` (committed to the repo, like the current `worldLocations.ts`).
- `GlobeView.tsx` imports only the generated `src/data/geoLabels.ts` — a plain array of plain objects — keeping the runtime bundle lean and avoiding any Node-only APIs (`require`, `fs`) in browser code.
- The script is a dev tool (run via `node scripts/generate-geo-labels.mjs`), not part of the Vite build pipeline, so `npm run build` never touches the raw source packages.

## Architecture

```
scripts/generate-geo-labels.mjs   (Node, dev-time only)
   reads: node_modules/world-countries, node_modules/all-the-cities
   writes: src/data/geoLabels.ts
                    |
                    v
src/data/geoLabels.ts             (generated, committed static data)
   exports: GeoLabel[] (countries + tiered cities)
                    |
                    v
src/app/components/GlobeView.tsx
   imports geoLabels
   computes Visible_Label_Set via getVisibleGeoLabels(altitude, geoLabels)
   merges with existing memory-badge entries (unchanged)
   passes combined array into .htmlElementsData(...)
```

## Components and Interfaces

### 1. Generation script — `scripts/generate-geo-labels.mjs`

Run manually/once (`node scripts/generate-geo-labels.mjs`) whenever the dataset needs regenerating. Not part of `npm run build`.

```js
import countries from 'world-countries';
import cities from 'all-the-cities';
import { writeFileSync } from 'fs';

const countryLabels = countries
  .filter((c) => c.independent)
  .map((c) => ({
    kind: 'country',
    name: c.name.common,
    lat: c.latlng[0],
    lng: c.latlng[1],
  }));

function tierForPopulation(population) {
  if (population >= 5_000_000) return 'tier1';
  if (population >= 1_000_000) return 'tier2';
  if (population >= 300_000) return 'tier3';
  return null;
}

const cityLabels = cities
  .map((c) => {
    const tier = tierForPopulation(c.population);
    if (!tier) return null;
    return {
      kind: 'city',
      name: c.name,
      lat: c.loc.coordinates[1],
      lng: c.loc.coordinates[0],
      population: c.population,
      tier,
    };
  })
  .filter(Boolean);

const output = `// AUTO-GENERATED by scripts/generate-geo-labels.mjs. Do not hand-edit.
export type GeoLabelKind = 'country' | 'city';
export type CityTier = 'tier1' | 'tier2' | 'tier3';

export interface GeoLabel {
  kind: GeoLabelKind;
  name: string;
  lat: number;
  lng: number;
  population?: number;
  tier?: CityTier;
}

export const geoLabels: GeoLabel[] = ${JSON.stringify([...countryLabels, ...cityLabels], null, 2)};
`;

writeFileSync('src/data/geoLabels.ts', output);
console.log(`Generated ${countryLabels.length} countries and ${cityLabels.length} cities.`);
```

### 2. Generated data module — `src/data/geoLabels.ts`

Replaces `src/data/worldLocations.ts`. Committed static output of the script above; a flat array of `GeoLabel` objects as defined in the `GeoLabel` interface shown above. `src/data/worldLocations.ts` is deleted once `GlobeView.tsx` no longer references it.

### 3. Label visibility selector — `src/app/components/geoLabelVisibility.ts` (new, pure, unit/property-testable module)

Extracting this filtering logic into its own small pure-function module (rather than inlining it in `GlobeView.tsx`) is what makes it property-testable independent of the DOM/globe.gl.

```ts
import { GeoLabel, CityTier } from '../../data/geoLabels';

export const CITY_TIER_ALTITUDE: Record<CityTier, number> = {
  tier1: 2.0,  // tier1 cities visible once altitude < 2.0
  tier2: 1.2,  // tier2 cities visible once altitude < 1.2
  tier3: 0.6,  // tier3 cities visible once altitude < 0.6
};

export const COUNTRY_HIDE_ALTITUDE = 0.6; // countries hidden once altitude < 0.6

/**
 * Pure function: given the full label dataset and current camera altitude,
 * returns only the labels that should be rendered (i.e. passed into
 * htmlElementsData), filtering out everything else so far-fewer DOM nodes
 * exist at any given zoom level.
 */
export function getVisibleGeoLabels(labels: GeoLabel[], altitude: number): GeoLabel[] {
  return labels.filter((label) => {
    if (label.kind === 'country') {
      return altitude >= COUNTRY_HIDE_ALTITUDE;
    }
    // city
    const threshold = CITY_TIER_ALTITUDE[label.tier as CityTier];
    return altitude < threshold;
  });
}
```

### 4. `GlobeView.tsx` changes

- Replace `import { worldLocations } from '../../data/worldLocations';` with `import { geoLabels } from '../../data/geoLabels';` and `import { getVisibleGeoLabels } from './geoLabelVisibility';`.
- In the data-effect (currently keyed on `[memories, onLocationClick, onMemoryClick, altitude]`), replace the unconditional `worldLocations.map(...)` with:

```ts
const visibleGeoLabels = getVisibleGeoLabels(geoLabels, altitude);
const geoLabelEntries = visibleGeoLabels.map((label) => ({
  kind: 'geo-label' as const,
  ...label,
  text: label.name,
  size: label.kind === 'country' ? 1.2 : label.tier === 'tier1' ? 1.1 : label.tier === 'tier2' ? 0.95 : 0.85,
}));
```

- `memoryBadgeEntries` construction is unchanged (Requirement 5.2 / Requirement 6.5 — memory badges are untouched and always included regardless of altitude/tier filtering).
- `combinedHtmlEntries = [...geoLabelEntries, ...memoryBadgeEntries]` — same concatenation pattern as today, just built from the filtered set instead of the full dataset.
- The `.htmlElement()` factory's `'geo-label'` branch keeps its existing style logic (color by `d.kind === 'country' ? ... : ...` — note: the field is renamed from `type` to `kind` with values `'country'`/`'city'` to match the new `GeoLabel` shape; update the two `d.type === 'country'` checks to `d.kind === 'country'`), but since entries are now pre-filtered by altitude tier, the font-size/opacity can simplify to a single "fade in" step instead of the old two-band logic — see below.
- Because filtering now happens before the array reaches `htmlElementsData`, the remaining opacity/font-size logic only needs to handle the *entry* transition (0 → visible) using a short CSS transition, rather than tracking multiple altitude bands inline. A label present in `combinedHtmlEntries` is always rendered at full target size/opacity (`d.kind === 'country' ? d.size * 10 : d.size * 9`px font, opacity `1`), and the `transition: opacity 0.3s ease` on the element handles the visual fade when a label newly mounts. This preserves Requirement 3.5 (unchanged 0.3s transition) while removing the old dual-threshold logic that no longer applies now that country/city visibility is tier-driven.

## Data Models

```ts
type GeoLabelKind = 'country' | 'city';
type CityTier = 'tier1' | 'tier2' | 'tier3'; // tier1 = world-major (pop >= 5M), tier2 = major (pop >= 1M), tier3 = mid-size (pop >= 300K)

interface GeoLabel {
  kind: GeoLabelKind;
  name: string;
  lat: number;
  lng: number;
  population?: number; // present for kind === 'city'
  tier?: CityTier;      // present for kind === 'city'
}
```

## Error Handling

- If the generation script encounters a country record missing `latlng` or a city record missing `population`/`loc.coordinates`, that record is skipped (`.filter(Boolean)` / guard checks) rather than producing malformed entries — since this runs at dev-time and writes a static file, a bad record would otherwise silently corrupt committed data.
- At runtime, `getVisibleGeoLabels` treats any city label with an unrecognized `tier` value as never visible (falls through `CITY_TIER_ALTITUDE` lookup to `undefined`, and `altitude < undefined` is `false`), failing closed rather than throwing.
- No network calls are introduced; the generated file is static, so there is no runtime fetch failure mode to handle.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system-essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Country mapping is a faithful, complete projection

For all lists of country records from `world-countries`, mapping them through the country-label transform produces exactly one output entry per record where `independent === true`, and each output entry's `name` equals the record's `name.common`, `lat` equals `latlng[0]`, and `lng` equals `latlng[1]`.

**Validates: Requirements 1.1, 1.2, 1.3**

### Property 2: City population-to-tier classification is total and boundary-correct

For any population value, the tier classification function returns `tier1` for population >= 5,000,000, `tier2` for population >= 1,000,000 and < 5,000,000, `tier3` for population >= 300,000 and < 1,000,000, and no tier (excluded) for population < 300,000 — with no population value mapping to more than one tier.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4**

### Property 3: City mapping preserves source fields

For all city records from `all-the-cities` that classify into a tier, the resulting `GeoLabel` entry's `name`, `lat`, `lng`, and `population` equal the source record's `name`, `loc.coordinates[1]`, `loc.coordinates[0]`, and `population` respectively.

**Validates: Requirements 2.5**

### Property 4: Visible label set is a monotonically nested function of altitude

For any fixed label dataset and any two altitudes `a1 < a2`, the visible label set at `a1` is a superset of the visible label set at `a2` (zooming in never hides a label that was visible while more zoomed out), and for any altitude, a label is included if and only if it satisfies its kind-specific altitude predicate (country visible iff altitude >= 0.6; city visible iff altitude < its tier's threshold).

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 4.1, 4.2**

### Property 5: Filtering excludes exactly the non-visible entries

For any label dataset and any altitude, every entry returned by `getVisibleGeoLabels` satisfies its visibility predicate for that altitude, and every entry in the dataset that satisfies the predicate appears in the returned result (no extra entries, no missing entries).

**Validates: Requirements 5.1**

### Property 6: Memory badge entries are unaffected by geo-label filtering

For any list of memories and any altitude, the number of `memory-badge`-kind entries in the combined array passed to `htmlElementsData` equals the number of memories, regardless of the altitude value or the geo-label dataset's contents.

**Validates: Requirements 5.2, 6.5**

## Testing Strategy

- **Unit tests** cover: the generation script's field mapping on a handful of representative fixture records (not the full 138k dataset — fixtures only), the static style-string output for country vs. city label elements (color/weight/text-shadow, Requirements 6.1-6.3), and that the 0.3s opacity transition string is present (Requirement 3.5).
- **Property tests** (fast-check, matching existing `devDependencies`) cover Properties 1-6 above, run against the pure functions (`tierForPopulation`/mapping helpers extracted from the generation script, and `getVisibleGeoLabels`), using generated fixture-shaped records and random altitude floats — not the live npm packages at test time, to keep tests fast and deterministic.
- Rotation pause/resume on hover and memory-badge click/hover behavior (Requirements 6.4, 6.5's interaction half) are pre-existing and unmodified by this feature; no new tests are added for them, but manual smoke-check during implementation confirms no regression.
